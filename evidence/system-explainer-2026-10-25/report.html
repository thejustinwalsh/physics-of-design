How Design Theory works: a source-bound explanation

Design Theory turns a product brief into editable, conditional design decisions, then checks what those decisions do in an actual renderer. It combines specialist measurements, finite mathematical search, optional local model selection, reusable recipes, runtime state machines and explicit verification obligations. Its output is a set of values, alternatives and conditions that an app can consume. The code does not establish a universal theory of beauty or generate an arbitrary component tree.

This explanation was prepared from repository source and retained JSON on 2026-10-25. The interactive explanation contains seven tiny machines. The manifest records exact capture time and SHA-256 hashes. Source links below point into frozen, line-numbered copies, so later implementation changes cannot silently alter this account. The teaching run was executed through existing exported implementation functions, without inference or native processes. Its generator and execution log are retained.

1. The workflow begins with meaning and measured inputs

A person or build agent authors the intent: audience, task, content, art direction, hard requirements and acceptable alternatives. context inspect reads a design document and returns its content identity. Dependent choices can bind that identity, so a changed brief is visible to cache logic. The gallery's bold visual direction comes from a recorded synthetic interview. That is an authored assumption, not evidence of human preference. See context implementation, gallery brief inside its retained session, and this explanation's own brief.

Measurements are specific to content, font bytes and renderer. A title's width is not a stable property of its font size alone: wording, axes, features, tracking, line breaking and available width matter. The typography inspector distinguishes font/shaping facts from browser geometry. Browser Range rectangles represent selection fragments; they are not raster ink. Baseline probes can fail or remain unknown. A declared CSS font axis does not prove the effective rasterized coordinate. Native Text/Yoga evidence has a different provider and cannot be manufactured by renaming a browser receipt. See typography inspector and DOM collection.

The specialist tools also inspect palette roles and contrast, motion response, material parameters and image descriptors. Their results become factual inputs or explicitly marked assumptions. The compact app entry point, kernel compile, converts three families of semantic decisions—measured text/row density, responsive region allocation and finite appearance alternatives—into the same staged engine. It reduces manual expression authoring. It does not compile a whole app from components. See kernel compiler and resolved output projection.

The CLI, MCP and exported functions are different access routes into this implementation. The MCP context layer can keep full results in a store while returning summaries and references, so a build agent need not repeatedly read a measurement matrix into its conversational context. The command registry exposes schemas for focused discovery. This explains a mechanism for reducing repeated payloads; it does not establish end-to-end coding-token savings. See command implementation, result store and summary dispatch.

2. Hard feasibility and preference are different questions

The energy program declares finite variables, derived expressions, scenarios and factors. Each factor carries provenance, a category, target bands, a scale and a mode. Multiple bands permit several acceptable regions. A nonzero target can express deliberate tension. The compiler orders derived dependencies, rejects cycles and unknown references, freezes the normalized program and hashes it. See schema and compiler.

For each factor/scenario pair, the implementation computes distance to the nearest target band, then divides by the factor's scale. A hard factor outside its bands adds a hard failure. A preference factor contributes weight × residual² to the aggregate energy. These are separate fields: a large preference weight cannot buy permission to violate a hard constraint. This is mathematical admissibility under the authored model, not browser verification or accessibility certification. See evaluation.

The tiny energy machine uses an explicitly invented teaching brief: title sizes 24–72px, a hard size cap, a quiet preference for 24–32px and a bold preference for 56–64px. Those targets are deliberately incompatible. Changing a weight changes which compromise ranks well; changing the hard cap changes eligibility. All nine combinations were actually evaluated by compileEnergy and searchEnergy. No font or renderer was involved. The example teaches the mechanism, not a recommended typography scale.

The search ranks candidates by hard failures, hard residual, then aggregate preference energy; canonical assignment order breaks remaining ties. It can enumerate the finite domain or use deterministic beam exploration. Budgets cap states, factor observations and expression operations. Exhaustiveness is a returned fact, not an assumption. Pareto comparison uses the individual preference contributions: an alternative is dominated when another is no worse on all and strictly better on at least one. pareto-diverse retention also preserves distinct assignments and reports incomplete comparison coverage. Equal factor vectors can still conceal visible differences. See search, dominance and return scope, and historical choice-effectiveness audit.

“Energy” is therefore a useful mathematical language for competing relationships. It has no physical unit here and is not a beauty probability. Musical intervals can be optional hypotheses for a particular relationship. The current generic energy program does not require music, a golden ratio, or literal spring physics.

3. A change has a dependency footprint

The typography graph declares what each node reads and what it depends on. Changing the first block's size affects shaping, layout and dependent relationships. Downstream layout depends on the previous block's layout, so a title change can move the paragraph. Changing a gap affects layout and whitespace without pretending that font metrics changed. A color change follows a different path. invalidated marks direct JSON-pointer overlaps, then walks the transitive dependency closure. See graph and invalidation.

The second tiny machine displays the actual dependency graph for examples/editorial.json and actual invalidation outputs. Highlighting a node means its inputs are affected; it does not mean the inspector has recomputed it or collected new geometry. This distinction matters: a stale receipt should disappear from current evidence even when an old screenshot still looks plausible.

4. Stages make decisions conditional, then cache their recipe

decision run traverses a dependency DAG. A stage searches a bounded numeric problem, retains alternatives and either selects mathematically or asks the optional local selector to choose from viable options. A later stage can bind variables selected by a predecessor. Neural selection happens after numerical exploration, outside the hot search loop. Separate counters distinguish searches, assignments, factor observations, requested/completed readouts, real neural calls, test-injected selectors and replay. See stage schema, stage execution and identity, and selection/save.

The explainer executed the existing mathematical editorial workflow. Its first run searched six assignments across two stages and chose a 640px column with 18px body text. Replay searched zero assignments, revalidated six saved assignments and reused two stage entries. After changing the column target, replay returned composition: stale and typography: blocked. Recomputing selected 720px and 20px. These are actual engine outputs for an estimated-advance example; they are not measured font-layout results. Inspect the complete run/replay/change inputs and outputs.

A recipe binds more than the selected values. Cache identities incorporate stage program, relevant context, predecessor keys and assignments, guards, search/selection policy and applicable checkpoint identity. Cached assignments and continuation witnesses are reevaluated; stored feasible flags are not trusted. A saved UI preset lacks these guarantees. In replay-only mode a stale stage blocks rather than silently searching. See revalidation path.

Optional bounded lookahead explores declared direct successors under retained parent alternatives. It can require a witnessed continuation and use successor target satisfaction among exact parent ties. It is not recursive global backtracking or a proof of the best full DAG path. A child policy change must invalidate a parent's choice when that choice depended on lookahead. Unknown or incomplete branches remain unknown. See lookahead identity and witness revalidation.

5. Runtime, validation and bindings are three different machines

The portable runtime resolves a chosen assignment into named regions and motion parameters for web or native consumers. The app state machine expresses states, transitions and bindings; it does not render components. The runtime checks input keys and finite values, matches named scenarios to their actual input vector, applies appropriate factor bands and rejects out-of-envelope or unresolved hard applicability. Naming an 834px input “phone” cannot make it the 390px phone scenario. Unsampled scenario overrides require an explicit base-band policy when applicable. A mathematical pass still returns pending-renderer-verification. See portable resolver and handoff/state machine implementation.

The XState validation machine answers whether a phase's required evidence has been supplied for the current design. A plan lists scenarios and obligations. Missing, stale, failed, unknown or wrong-kind receipts block progression. Unsupported behavior blocks by default; an explicitly authored record policy can permit progression while retaining the limitation. Synthetic review cannot satisfy a human-review requirement. The gate does not run tools or authenticate receipt files. A fabricated declaration could satisfy its schema; underlying evidence must still be inspected. The explainer's gate machine deliberately uses authored teaching declarations and labels them as such. See receipt matching and gate scope.

The output-binding checker answers a narrower question: did the expected selected property reach the named rendered target, with the right unit, provider, scenario and identities? It resolves a source pointer into a typed expected-value manifest, then compares supplied observations. It distinguishes pass, override, stale, unbound, wrong-evidence, unknown and unsupported outcomes. An 18px value observed as 20px is an override; an iOS provider cannot attest a web binding. A matching value supports consistency, not causal influence, task success or whole-app accessibility. See binding schema and comparison.
