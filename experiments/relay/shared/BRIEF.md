# Relay — frozen product and behavior brief v1

Recorded 2026-10-25. Scope: one substantial observability and incident-operations demo for SREs, built independently by Luna, Sol and Astra from identical inputs. This is an authored product brief based on the user’s requested experiment. No interview was conducted, no human preference evidence is claimed, and no simulated respondent is presented as a user.

## Product outcome

An on-call engineer can recognize a production latency regression, isolate the responsible service and diagnostic trace, coordinate an incident, and verify that all linked operational state changed. The product is a working application with useful secondary tasks and dense information. It is not a promotional landing page. All telemetry, people, service names and incidents are visibly labeled **Demo · synthetic data**. There is no external backend, authentication, live monitoring claim or implied notification delivery.

## Frozen data

Run `node experiments/relay/shared/generate-fixtures.mjs --check`. `fixtures.json` is generated from seed `20261024` with stable demo time `2026-10-24T18:00:00.000Z`; it contains 120 services, 36 incidents (22 initially active), 1,000 traces, 24 alert rules, six teams, 18 synthetic members and 48 five-minute buckets covering 14:00–18:00 UTC. Use the supplied file directly; do not create an easier alternative dataset. IDs and relation integrity are shared test anchors. The generator, types and fixtures contain no presentation/UI code.

Units are explicit: latency/duration in ms, request counts as integers, request rate in req/s (`count / bucket seconds`), error rate as `errorCount / requestCount` (0–1 internally, percentage visually), SLO as a percent, and times as ISO UTC. Request counts and errors aggregate by summing. Percentiles are synthetic aggregate snapshots supplied in `serviceSeries` and `fleetSeries`; **never average service p95 values** or pretend 1,000 diagnostic traces are the full request population. Fleet quantiles are independent authored demo observations. Time ranges are 15m/1h/4h relative to the frozen clock, not the host’s current date. Charts label UTC unless the user changes display timezone. A live-looking animation may never add invented network samples.

## Primary diagnosis and coordination flow

The shared anchor is `service-001` checkout-api → `INC-1042` Checkout tail latency elevated → `trace-000001` → `service-002` inventory-cache. The last service bucket has checkout p95 **1,850 ms** against a **450 ms** target. The diagnostic trace lasts **2,180 ms**; `cache.pool.acquire` occupies **1,340 ms**, nested inside `inventory.reserve`, and pool active/limit are both 64. These observations support an authored hypothesis of connection-pool saturation; do not claim causal proof from a single trace.

1. From Overview select 1h, inspect the latency rise and open checkout-api. Range/cursor identity stays consistent in linked charts.
2. From the service open INC-1042. Assign **Ari Vale (`member-01`)** and acknowledge. Queue, owner chip, service incident list and timeline immediately agree.
3. Mark investigating; open the linked diagnostic trace; select the pool-acquisition span and read its parent, duration and attributes. Back returns to the same incident and list context.
4. Add the note “Raised the demo inventory-cache pool limit; verifying recovery.” Resolve with “Synthetic mitigation verified; follow-up pool sizing review scheduled.” Both are demo operator records, not a backend action.
5. Assert active incident count **22 → 21**, unassigned active **10 → 9**, INC-1042 resolved in every view, assigned member retained, resolved timestamp present, alert-001 healthy with its active incident link cleared, exactly one assignment/acknowledgement/investigation/note/resolution event and audit entry. Repeating acknowledgement/resolution is an idempotent no-op with no duplicate events.

Historical charts and traces remain unchanged by incident resolution. Do not fabricate recovery telemetry. Service health derives from current metric thresholds, while active incident counts derive from incident status; resolving a workflow cannot make a still-breaching metric healthy. Overview must be able to show “21 active incidents” and a service still above target. `service-002` also has independent INC-1043; resolving INC-1042 does not resolve unrelated work. Alert-001’s workflow event is cleared on manual resolution; label subsequent rule evaluation separately and require an explicit **Evaluate demo rules** action before it can fire again from the frozen samples.

## Canonical state and mutation rules

Maintain one canonical store keyed by IDs. Derive badges/counts/filtered tables from it; do not maintain unrelated copies for each route. Fixture data is immutable baseline; local user state is versioned and namespaced per build so running three apps does not share state accidentally. Reset restores the exact fixture. User mutations are local only and clearly described as such.

Assign accepts existing members and appends timeline/audit. Acknowledge sets acknowledgedAt only once and requires a non-resolved incident; investigation requires acknowledgement. Resolve requires a nonempty note, retains owner and acknowledgement history, sets resolvedAt and clears corresponding firing-event links. Disabled rules become muted. Re-enable/evaluate uses the explicitly displayed demo clock and latest N buckets, not a real server; p95 rule compares the **maximum supplied bucket p95** over its window (label this policy), error-rate rule uses weighted `sum(errorCount)/sum(requestCount)`. New firing events reuse an active matching incident or create a clearly synthetic incident with a monotonic local ID. Do not remove historical incident-rule references. Changing a rule to a different service resets its active event link and leaves history intact. Validate names/finite positive latency/0–100% error threshold/service/team/window before save; cancel preserves stored values.

User action time is deterministic demo time plus one second per committed mutation, with a persisted sequence. No action may precede the entity’s existing event times. Audit records include actor, entity ID, action, time and human-readable change. Prefer explicit failure and retry over optimistic success claims that did not commit.

## Shared interaction behavior

Global time range, selected series bucket, environment and team filters are visible and persistent during linked navigation. Route tables also preserve their own sort/page/query; filter changes reset only the relevant page. Page sizes 15/30/60, result count and current-page selection scope are explicit. Numeric sorting uses numeric values, severity uses P1/P2/P3 order and ties use stable IDs. Search covers actual names/IDs/route text. Reset filters produces a known baseline. Selection remains identified by IDs and is either retained across pages or explicitly shown as current-page selection; no ambiguous hidden bulk action.

Cmd/Ctrl+K opens route/entity/action search, with keyboard focus, arrows, Enter, Escape and focus restoration. “/” focuses local search outside inputs. Native offers an equivalent visible search/command action; hardware shortcuts are optional when unsupported. Charts expose the same bucket through pointer/touch and keyboard stepper, a pinned/shared cursor, units, date, series legend and text summary. A tooltip cannot be the only access to a value. Focus order follows visual task order. Tab/Enter/Space, screen-reader labels, state announcements, dialog containment and Escape/back work. Avoid hover-only actions.

## Recovery, persistence and acceptance

Provide a clearly labeled demo-state control for loading/offline/error. Loading reserves structure without misleading stale success; offline retains locally loaded content and permits local mutations labeled “saved locally”; error offers retry without discarding query/selection. Empty filter results explain the active filters and offer clear/reset. Local storage failure is announced with an in-memory fallback and export; it must not be described as a saved session. Native uses a supported native storage adapter, web a web adapter. No backend/network calls are needed for the demo.

Required scenarios: phone 390×844, small phone 320×740, narrow window 768×900, iPad 834×1194, desktop 1440×1000 and wide 1920×1080; 100% and 150% text plus native supported accessibility text enlargement; changed long service/incident text; dark/light; reduced motion; offline/loading/error/empty. On phone, show prioritized summaries and explicit expandable columns/details; on iPad use a workable navigation/list/detail topology; desktop supports dense comparison. Scrolling a table is acceptable when labeled and reachable; clipping controls or silently dropping data is not. Test actual continuous pointer drag, keyboard/touch selection, scroll, live state updates, rotation/resizing, navigation disposal and hidden/offscreen rendering suspension. Measure actual native safe content roots and platform text geometry. Chromium/WebKit evidence does not certify physical Safari or native parity.

The final proof executes the full primary flow plus filter/sort/page/select, saved-view replay/delete, rule validation/save/toggle/evaluation, command search, theme/motion/persistence/reset and recovery on each applicable platform. Keep design/fixture/source/recipe/scenario identities, current geometry, screenshots and failures. Use the validation phase matrix in TOOL-COVERAGE.md; ordered repository verification precedes publication. Human preference, award quality, comparative token savings and hardware performance remain unproven until actually tested.
