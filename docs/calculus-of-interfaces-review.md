# Calculus of Interfaces compared with Design Theory

Reviewed November 4, 2026. The recommendation is to add sensitivity analysis and responsive regime analysis to our existing expression engine. Keep the brief, choice machine, actual typography measurements and renderer validation. This is a proposed extension, not newly implemented functionality or evidence of superior visual taste.

The [Vercel Labs prototype](https://calculus-of-interfaces.vercel.app/) represents one authored layout as an arithmetic graph. It evaluates that graph numerically, with softened thresholds, with forward derivatives and with intervals. Its examples connect those views to resizing, transitions, optimization and validation. The stated limits matter: manual construction, monospace character-count wrapping, illustrative device data and proofs that exclude floating-point rounding. It does not convert arbitrary React into a verified layout function.

I inspected the published explanation and delivered JavaScript, including the evaluators and breakpoint, transition and verification implementations. I did not run its interactive UI, benchmark it, or independently certify its proof implementation. The local snapshot records the URL, retrieval time and SHA-256 of the HTML and bundle in `artifacts/research/calculus-of-interfaces-20261104/snapshot.json`. No third-party application code is included in this tracked report. The linked [Handwired project](https://github.com/chenglou/handwired) explains the underlying arithmetic-program idea; a hand-constructed arithmetic network does not require another learned selector.

Our comparison uses source at integration checkpoint `c8b28d2`, with the concurrent material-quantity/readout work kept separate. The frozen Relay builders use `8564509`; this research changes none of their inputs. Source inspection establishes mechanisms, not current device performance or a preference win.

We should describe our advantage as stronger integration and evidence boundaries, not proven better design.

The useful mathematical separation is:

`F(theta, z) -> geometry and declared consequences`

`E(theta | brief, scenarios) -> separate authored preference factors`

Here `theta` contains editable choices; `z` contains width, scale, content/font identity and platform context. Our existing local energy differences answer which neighboring choice reduces this brief's residuals. A geometry Jacobian `J_F` answers which elements change, and by how much, before preferences are applied. Those are different questions. Neither quantity is aesthetic truth.

Fold back the following, in this order:

1. **Geometry sensitivities and responsive regimes.** Extend the existing AST interpreter rather than create another planner. Support derivatives on a declared differentiable subset, mark kinks/discontinuities explicitly, and expose each event's cause and input interval. Combine algebraic topology thresholds with separately labeled renderer-observed text brackets. This would make a heading-size change explain its consequences for line count, pane width and adjacent space. It also gives our inspection drawings useful dependency information instead of decorative arrows.

2. **Counterexample-driven verification.** Add tests immediately on both sides of identified events, at the event's tie condition, and inside each region. Cover width, user enlargement, content, axes and platform; phone/iPad/desktop checkpoints remain necessary but insufficient. When a renderer disagrees, retain the counterexample and revise the applicable model. Empirical text observations cannot silently become certified continuous bounds. This should reduce wasted uniform sampling while making narrow failures harder to miss; that cost benefit must be measured.

3. **Conservative mathematical bounds.** Add interval evaluation and branch-aware subdivision for a small supported subset first. Return a mathematical pass, failure witness, unresolved region or unsupported operation, with exact input applicability and arithmetic policy. Division through zero, logarithm/square-root domains, varying exponents and ambiguous branch conditions require explicit handling. Rigorous floating-point bounds need sound rounding/error treatment; ordinary JavaScript endpoints are insufficient. [Boost's interval documentation](https://www.boost.org/doc/libs/latest/libs/numeric/interval/doc/interval.htm#numbers) explains that inclusion guarantee and rounding requirement. Such a result certifies the modeled relationship within its domain, not browser text, task accessibility or visual preference.

4. **Transition paths before temporal playback.** Use layout sensitivities and finite topology changes to plan an admissible route between chosen states. A possible brief-specific path cost is normalized, role-weighted geometric travel plus explicit jump penalties; enforce content, focus identity and hit-region constraints separately. Feed the route to the existing retargetable spring runtime. A brief can request a sharp accent or tension band: minimizing every visible change would erase expression. Cache the route with its source, content, platform and applicability identities, so traversal does not require repeated selector calls.

5. **An explanation surface centered on consequences.** One live product, its actual geometry, a width/text-scale map, a selected factor, its derivatives or threshold brackets, and clear evidence labels would explain our system better than a large gallery of disconnected equations. Link the inspection UI to current elements and input identities. Show predicted, measured, mathematical and unknown states separately. This belongs in the existing specimen/inspection MCP App; it does not require expanding default tool discovery.

6. **Distribution-aware reporting only after those basics.** With attributed real usage data, report expected soft costs and the size of risky regions alongside worst-case results. Never average away clipping, inaccessible controls or enlarged-text failures. Without data, use declared synthetic scenarios and say so. Lower expected page height is not a universal design objective.

Several adoption details deserve tests before implementation. Independent calculations and current-evaluator checks are retained in `artifacts/research/calculus-of-interfaces-20261104/math-checks.mjs` and `math-checks.json`:

- A softened threshold has value `sigmoid(0/tau) = 0.5` at its boundary for every positive `tau`. Exact strict/inclusive branch ownership must remain explicit; annealing does not settle that tie.
- A first-order reuse rule is exact only for an affine output within its applicable region. Our AST supports nonlinear expressions: for `sqrt(width)`, linearizing at 400 and predicting at 900 gives 32.5 instead of 30. Reuse needs a proven affine classification or a stated approximation/error bound.
- Softness is not time. For threshold input moving at speed `v`, the logistic transition between epsilon and `1-epsilon` takes `2*s*tau*log((1-epsilon)/epsilon)/abs(v)`. A 4px transition scale at 100px/s takes about 0.368s between 1% and 99%; doubling input speed halves that duration. A motion adapter still needs a clock, interruption policy and reduced-motion behavior.
- Our lazy `if` correctly avoids an inactive `log2(-1)` branch. Computing all branches and multiplying inactive results by zero can introduce invalid arithmetic. Retain that semantic protection and avoid an uncontrolled explosion of topology alternatives.

These are scoped adoption hazards, not a claim that the complete third-party UI was independently tested or found defective. Complex-width experiments and signal compression are not priorities for our agent workflow. They do not close our current binding, native playback or visual-quality gaps.

The acceptance experiment should use an existing real-content app: compare the present engine with sensitivity/regime-guided exploration under the same brief and measurements. Require deterministic equivalence on the supported subset, boundary/tie tests, an intentionally hidden narrow failure, honest unresolved outcomes, changed-font/content invalidation and actual web/native finalist checks. Count numeric work, renderer calls, selector calls, replay reuse, wall time and main-agent tokens separately. Award-level quality and human preference still require their own evidence. The immediate opportunity is better exploration and fewer missed transitions, without adding another model or weakening our current facts-versus-preferences boundary.
