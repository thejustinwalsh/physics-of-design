# How Design Theory works: a source-bound explanation

Design Theory turns a product brief into **editable, conditional design decisions**, then checks what those decisions do in an actual renderer. It combines specialist measurements, finite mathematical search, optional local model selection, reusable recipes, runtime state machines and explicit verification obligations. Its output is a set of values, alternatives and conditions that an app can consume. The code does not establish a universal theory of beauty or generate an arbitrary component tree.

This explanation was prepared from repository source and retained JSON on **2026-10-25**. The [interactive explanation](../evidence/system-explainer-2026-10-25/index.html) contains seven tiny machines. [The manifest](../evidence/system-explainer-2026-10-25/manifest.json) records exact capture time and SHA-256 hashes. Source links below point into frozen, line-numbered copies, so later implementation changes cannot silently alter this account. [The teaching run](../evidence/system-explainer-2026-10-25/engine-results.json) was executed through existing exported implementation functions, without inference or native processes. Its [generator](../evidence/system-explainer-2026-10-25/generate.ts) and [execution log](../evidence/system-explainer-2026-10-25/execution.log) are retained.

## 1. The workflow begins with meaning and measured inputs

A person or build agent authors the intent: audience, task, content, art direction, hard requirements and acceptable alternatives. `context inspect` reads a design document and returns its content identity. Dependent choices can bind that identity, so a changed brief is visible to cache logic. The gallery's bold visual direction comes from a recorded synthetic interview. That is an authored assumption, not evidence of human preference. See [context implementation](../evidence/system-explainer-2026-10-25/source.html#design-context-22), [gallery brief inside its retained session](../evidence/system-explainer-2026-10-25/receipts/artifacts--design-field-streaming-selector--gallery-session.json), and [this explanation's own brief](../evidence/system-explainer-2026-10-25/DESIGN.md).

Measurements are specific to content, font bytes and renderer. A title's width is not a stable property of its font size alone: wording, axes, features, tracking, line breaking and available width matter. The typography inspector distinguishes font/shaping facts from browser geometry. Browser Range rectangles represent selection fragments; they are not raster ink. Baseline probes can fail or remain unknown. A declared CSS font axis does not prove the effective rasterized coordinate. Native Text/Yoga evidence has a different provider and cannot be manufactured by renaming a browser receipt. See [typography inspector](../evidence/system-explainer-2026-10-25/source.html#typography-inspection-65) and [DOM collection](../evidence/system-explainer-2026-10-25/source.html#typography-browser-2).

The specialist tools also inspect palette roles and contrast, motion response, material parameters and image descriptors. Their results become factual inputs or explicitly marked assumptions. The compact app entry point, `kernel compile`, converts three families of semantic decisions—measured text/row density, responsive region allocation and finite appearance alternatives—into the same staged engine. It reduces manual expression authoring. It does not compile a whole app from components. See [kernel compiler](../evidence/system-explainer-2026-10-25/source.html#relational-kernels-192) and [resolved output projection](../evidence/system-explainer-2026-10-25/source.html#relational-kernels-733).

The CLI, MCP and exported functions are different access routes into this implementation. The MCP context layer can keep full results in a store while returning summaries and references, so a build agent need not repeatedly read a measurement matrix into its conversational context. The command registry exposes schemas for focused discovery. This explains a mechanism for reducing repeated payloads; it does not establish end-to-end coding-token savings. See [command implementation](../evidence/system-explainer-2026-10-25/source.html#commands-1), [result store](../evidence/system-explainer-2026-10-25/source.html#mcp-context-3) and [summary dispatch](../evidence/system-explainer-2026-10-25/source.html#mcp-context-227).

## 2. Hard feasibility and preference are different questions

The energy program declares finite variables, derived expressions, scenarios and factors. Each factor carries provenance, a category, target bands, a scale and a mode. Multiple bands permit several acceptable regions. A nonzero target can express deliberate tension. The compiler orders derived dependencies, rejects cycles and unknown references, freezes the normalized program and hashes it. See [schema](../evidence/system-explainer-2026-10-25/source.html#energy-60) and [compiler](../evidence/system-explainer-2026-10-25/source.html#energy-235).

For each factor/scenario pair, the implementation computes distance to the nearest target band, then divides by the factor's scale. A hard factor outside its bands adds a hard failure. A preference factor contributes `weight × residual²` to the aggregate energy. These are separate fields: a large preference weight cannot buy permission to violate a hard constraint. This is mathematical admissibility under the authored model, not browser verification or accessibility certification. See [evaluation](../evidence/system-explainer-2026-10-25/source.html#energy-310).

The tiny energy machine uses an explicitly invented teaching brief: title sizes 24–72px, a hard size cap, a quiet preference for 24–32px and a bold preference for 56–64px. Those targets are deliberately incompatible. Changing a weight changes which compromise ranks well; changing the hard cap changes eligibility. All nine combinations were actually evaluated by `compileEnergy` and `searchEnergy`. No font or renderer was involved. The example teaches the mechanism, not a recommended typography scale.

The search ranks candidates by hard failures, hard residual, then aggregate preference energy; canonical assignment order breaks remaining ties. It can enumerate the finite domain or use deterministic beam exploration. Budgets cap states, factor observations and expression operations. Exhaustiveness is a returned fact, not an assumption. Pareto comparison uses the individual preference contributions: an alternative is dominated when another is no worse on all and strictly better on at least one. `pareto-diverse` retention also preserves distinct assignments and reports incomplete comparison coverage. Equal factor vectors can still conceal visible differences. See [search](../evidence/system-explainer-2026-10-25/source.html#energy-567), [dominance and return scope](../evidence/system-explainer-2026-10-25/source.html#energy-730), and [historical choice-effectiveness audit](../evidence/system-explainer-2026-10-25/receipts/artifacts--choice-effectiveness--report.json).

“Energy” is therefore a useful mathematical language for competing relationships. It has no physical unit here and is not a beauty probability. Musical intervals can be optional hypotheses for a particular relationship. The current generic energy program does not require music, a golden ratio, or literal spring physics.

## 3. A change has a dependency footprint

The typography graph declares what each node reads and what it depends on. Changing the first block's size affects shaping, layout and dependent relationships. Downstream layout depends on the previous block's layout, so a title change can move the paragraph. Changing a gap affects layout and whitespace without pretending that font metrics changed. A color change follows a different path. `invalidated` marks direct JSON-pointer overlaps, then walks the transitive dependency closure. See [graph](../evidence/system-explainer-2026-10-25/source.html#graph-4) and [invalidation](../evidence/system-explainer-2026-10-25/source.html#graph-103).

The second tiny machine displays the actual dependency graph for `examples/editorial.json` and actual invalidation outputs. Highlighting a node means its inputs are affected; it does not mean the inspector has recomputed it or collected new geometry. This distinction matters: a stale receipt should disappear from current evidence even when an old screenshot still looks plausible.

## 4. Stages make decisions conditional, then cache their recipe

`decision run` traverses a dependency DAG. A stage searches a bounded numeric problem, retains alternatives and either selects mathematically or asks the optional local selector to choose from viable options. A later stage can bind variables selected by a predecessor. Neural selection happens after numerical exploration, outside the hot search loop. Separate counters distinguish searches, assignments, factor observations, requested/completed readouts, real neural calls, test-injected selectors and replay. See [stage schema](../evidence/system-explainer-2026-10-25/source.html#decision-workflow-45), [stage execution and identity](../evidence/system-explainer-2026-10-25/source.html#decision-workflow-884), and [selection/save](../evidence/system-explainer-2026-10-25/source.html#decision-workflow-1210).

The explainer executed the existing mathematical editorial workflow. Its first run searched six assignments across two stages and chose a 640px column with 18px body text. Replay searched zero assignments, revalidated six saved assignments and reused two stage entries. After changing the column target, replay returned `composition: stale` and `typography: blocked`. Recomputing selected 720px and 20px. These are actual engine outputs for an estimated-advance example; they are not measured font-layout results. Inspect [the complete run/replay/change inputs and outputs](../evidence/system-explainer-2026-10-25/engine-results.json).

A recipe binds more than the selected values. Cache identities incorporate stage program, relevant context, predecessor keys and assignments, guards, search/selection policy and applicable checkpoint identity. Cached assignments and continuation witnesses are reevaluated; stored feasible flags are not trusted. A saved UI preset lacks these guarantees. In replay-only mode a stale stage blocks rather than silently searching. See [revalidation path](../evidence/system-explainer-2026-10-25/source.html#decision-workflow-949).

Optional bounded lookahead explores declared direct successors under retained parent alternatives. It can require a witnessed continuation and use successor target satisfaction among exact parent ties. It is not recursive global backtracking or a proof of the best full DAG path. A child policy change must invalidate a parent's choice when that choice depended on lookahead. Unknown or incomplete branches remain unknown. See [lookahead identity](../evidence/system-explainer-2026-10-25/source.html#decision-workflow-579) and [witness revalidation](../evidence/system-explainer-2026-10-25/source.html#decision-workflow-807).

There is retained evidence of real local selection, separate from this explainer's model-free run. The gallery session records **7 numeric searches, 3,132 assignments and 2 actual local neural readouts**, with no test selector calls. Its model provenance names Qwen3.5-4B, a checkpoint SHA and a restricted-option last-position logit readout with no generated tokens. A matching replay records **0 searches, 18 revalidations, 2 cache hits and 0 neural calls**. The stage observations include local latencies; these do not establish a universal speed claim. The same receipt retains Chromium finalist geometry for six width/text-scale scenarios. It does not establish subjective quality or all material/motion behavior. [Exact session receipt](../evidence/system-explainer-2026-10-25/receipts/artifacts--design-field-streaming-selector--gallery-session.json).

## 5. Runtime, validation and bindings are three different machines

The portable runtime resolves a chosen assignment into named regions and motion parameters for web or native consumers. The app state machine expresses states, transitions and bindings; it does not render components. The runtime checks input keys and finite values, matches named scenarios to their actual input vector, applies appropriate factor bands and rejects out-of-envelope or unresolved hard applicability. Naming an 834px input “phone” cannot make it the 390px phone scenario. Unsampled scenario overrides require an explicit base-band policy when applicable. A mathematical pass still returns `pending-renderer-verification`. See [portable resolver](../evidence/system-explainer-2026-10-25/source.html#decision-runtime-54) and [handoff/state machine implementation](../evidence/system-explainer-2026-10-25/source.html#decision-machine-178).

The XState validation machine answers whether a phase's required evidence has been supplied for the current design. A plan lists scenarios and obligations. Missing, stale, failed, unknown or wrong-kind receipts block progression. Unsupported behavior blocks by default; an explicitly authored record policy can permit progression while retaining the limitation. Synthetic review cannot satisfy a human-review requirement. The gate does not run tools or authenticate receipt files. A fabricated declaration could satisfy its schema; underlying evidence must still be inspected. The explainer's gate machine deliberately uses authored teaching declarations and labels them as such. See [receipt matching](../evidence/system-explainer-2026-10-25/source.html#validation-machine-134) and [gate scope](../evidence/system-explainer-2026-10-25/source.html#validation-machine-270).

The output-binding checker answers a narrower question: did the expected selected property reach the named rendered target, with the right unit, provider, scenario and identities? It resolves a source pointer into a typed expected-value manifest, then compares supplied observations. It distinguishes `pass`, `override`, `stale`, `unbound`, `wrong-evidence`, `unknown` and unsupported outcomes. An 18px value observed as 20px is an override; an iOS provider cannot attest a web binding. A matching value supports consistency, not causal influence, task success or whole-app accessibility. See [binding schema](../evidence/system-explainer-2026-10-25/source.html#output-bindings-43) and [comparison](../evidence/system-explainer-2026-10-25/source.html#output-bindings-229).

## 6. The specialties keep their own evidence boundaries

| Specialty | Present mechanism | What it cannot establish alone |
| --- | --- | --- |
| Typography | Font/shaping inspection, browser fragments/baseline probes, measured scenario cells and native geometry providers | Raster ink from Range boxes; fallback face identity from a load check; native parity from browser measurements |
| Color | Color conversion, role/state palette checks, joint candidate repairs, contrast calculations | Final contrast of an unknown translucent backdrop or every pose of a moving composite |
| Composition | Finite variables, explicit target bands, region bindings and conditional responsive scenarios | Semantic task success, all omitted screen sizes or the best unsearched design |
| Motion | Analytic springs and driven target updates; position/velocity preserved at retarget; separate target work and dissipation | Browser smoothness, hardware power or motion accessibility from equations alone |
| Material | Relative linear-RGB Lambert/GGX probe, Three parameter mapping, seeded texture data, DOM CSS/GPU adapters | Full light transport, universal physical accuracy, native dynamic finish, or beautiful pairings |

The seventh machine uses actual `contrastRatio`, `createDrivenMotion` and `probeSurface` outputs. Motion time is scrubbed, so no loop is required. At 0.5 seconds the target changes from 1 to 0.4; the anchor changes while position and velocity remain continuous. That physical spring energy is a different quantity from dimensionless design preference energy. The material example reports relative linear radiance for three roughness values at fixed light/view directions; it intentionally does not pretend those numbers are a renderer image. See [contrast](../evidence/system-explainer-2026-10-25/source.html#color-120), [driven motion](../evidence/system-explainer-2026-10-25/source.html#motion-dynamics-37), and [surface probe](../evidence/system-explainer-2026-10-25/source.html#surface-63).

Retained DOM/GPU receipts include 55 passing checks for sampled composite appearance, real reflow, context loss/fallback, resource retention, reduced motion, offscreen work and disposal. A separate gallery material integration receipt records 133 passing checks. CSS finishes are appearance approximations; the GPU shader shares defined Lambert/GGX conventions but adds authored ambient/light/display policies. These tests do not establish physical Safari thermals, sensor behavior or every supplied backdrop. [GPU receipt](../evidence/system-explainer-2026-10-25/receipts/artifacts--dom-surfaces-gpu--summary.json), [integration receipt](../evidence/system-explainer-2026-10-25/receipts/artifacts--design-theory--material-integration--report.json).

## 7. What the evidence supports today

The retained kernel proof records 13 numeric assignments over three searches, source stability, output-binding verification and deliberate override detection. Its stated scope is current Chromium text plus deterministic compiler/analyzer/search/binding behavior. It is not a finished Relay app or native kernel geometry proof. [Kernel receipt](../evidence/system-explainer-2026-10-25/receipts/artifacts--relational-kernels-final--receipt.json).

There is actual native evidence elsewhere in the repository: the retained Expo proof is complete for its source identity, with web and Expo Go iOS/Android observations and native input actions. Its limits explicitly distinguish simulator/emulator evidence from hardware, app-controlled twofold text enlargement from OS Dynamic Type, static native finish from web shaders, and measured widths/line heights from declared native font size. The independent blank-template smoke receipt has eight passing checks. That proves the tested shell and primitive adapters; it does not prove a later builder-produced app. [Expo proof](../evidence/system-explainer-2026-10-25/receipts/artifacts--expo-design-theory--proof.json), [template smoke proof](../evidence/system-explainer-2026-10-25/receipts/artifacts--expo-template-smoke--proof.json).

At the initial receipt capture, the full verification summary contained **33 of 34 stage results**, `complete: false`, `passed: false` and no final source-stability result. The [initial frozen receipt](../evidence/system-explainer-2026-10-25/receipts/artifacts--verification-design-theory-final--summary.json) remains historical. A later source-stable full run ended with an interrupted Android matrix stage; its result has `code: null`. The retained recovery metadata attributes this to the emulator/bridge disappearing. The [interruption summary](../evidence/system-explainer-2026-10-25/receipts/artifacts--verification-design-theory-android-interruption--summary-recovery-snapshot.json) is preserved separately.

**Update verified from the actual summary at 15:20:20Z:** the final receipt contains **34 stage results**, `complete: true`, `passed: true` and `sourceStable: true`. Recovery reused the 33 successful stages and reran the final Android matrix against the same source identity, `84bc53e57d77fd4d4e5a0bb015fb17054d2bd523661eae09d46d50d29527b99b`. This was a bounded recovery, not 34 newly repeated stages. The [successful recovery summary](../evidence/system-explainer-2026-10-25/receipts/artifacts--verification-design-theory-final--summary-recovery-snapshot.json) includes prior-summary and runner hashes; the manifest records both later copies. This explainer performs no Relay app build and makes no claim about later concurrent builders.

The interruption's evidence is incomplete: the retry producer truncated the shared partial observation file before a full separate copy was retained. The original failed summary and stage logs remain elsewhere, and this bundle preserves a [compact diagnostic excerpt](../evidence/system-explainer-2026-10-25/receipts/android-interruption-diagnostic-excerpt.json) with three timeouts and no Android device. The cause of the emulator process exit is unknown. The successful retry does not restore the missing historical rows.

Human preference, award quality, musical advantage and end-to-end token savings remain open. The retained workflow comparison covered one matched task, guidance-only Impeccable, an older toolkit snapshot and incomplete primary token comparability. It cannot rank the current system as a winner. Synthetic critique can expose a hypothesis or defect; it does not become human preference evidence. [Comparison adjudication](../evidence/system-explainer-2026-10-25/receipts/evidence--workflow-comparison-2026-10-25--evaluation--adjudication.json).

The useful promise supported by these mechanisms is narrower and practical: a choice can retain why it was considered, what conditions it obeys, what alternatives survived, which changes invalidate it, what the app consumed and what was actually measured. Judgment still supplies the brief and evaluates the result.

It preserves existing source/receipt snapshots and refuses to run against changed source hashes; create a separate snapshot for another revision.
