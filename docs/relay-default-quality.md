# Does Design Theory improve default designs?

Relay is the working integration product. Its current, repaired implementation is not a first-pass comparison result: it began as a separate copy of Sol's frozen implementation and has received later fixes. The frozen Luna, Sol and Astra builds share the toolkit and can reveal model and tool usability differences; they cannot isolate the toolkit's effect. The [older matched workbench trial](workflow-comparison.md) has no human preference result and incomplete control-arm token usage. Neither establishes better defaults or token savings.

This is a prospective evaluation plan, not a record of executed trials or collected ratings. Keep the original builder outcomes, failures and usage separate from integration repairs. The existing [matched-workflow runner](../scripts/compare-design-workflows.mjs) provides useful isolation and audit machinery, but its old workbench task, time limit and static rating page are not a ready Relay app experiment. Adapt and verify those contracts before launching a new comparison. Do not silently reuse its 900-second deadline: this project's builder policy is streaming completion without an imposed time budget.

## Inspect the product now

Use the same Relay build on phone, iPad/narrow window and desktop. Start from clean demo state, choose **Diagnose checkout**, open the linked incident and trace, inspect the pool evidence, coordinate the response, then resolve it. Reload and check that the resolution persists and linked counts agree. Try filtering and saving a service view, validating/editing an alert rule, command navigation, offline recovery, enlarged text, variable-font controls and reduced motion. All incidents and telemetry are synthetic.

Open **Inspect** to see current element geometry and the responsive consequence map. The displayed derivative, compatibility or energy explains a declared relationship; it does not rate the design. Note where hierarchy, dense data, material/light, touch interaction or motion help or obstruct the task. A browser preview or emulated tablet is not a native device test.

The current executable checks are:

```sh
npm run build
node scripts/prove-relay-static.mjs
node scripts/prove-relay-web.mjs
npm run verify
```

The static producer runs app tests/types and Expo web/iOS/Android exports, including execution of the emitted web toolkit factories. The browser proof checks actual Chromium/WebKit task flows, pointer and keyboard control, plot paint/anatomy, current property bindings, live inspection, embedded root dimensions, responsive regime boundaries/interiors, changed text/enlargement, recovery and persistence. The ordered headless lane remains required before publication. Static native exports and native-driver configuration do not establish native interactions, animation trajectory, native iPad or physical Safari performance. Retained receipts and their source identities determine what passed at each build; this document is not a pass receipt.

## Isolate the effect of the tools

Freeze the toolkit, skill/guidance, brief, neutral Expo/React Native/StyleX scaffold, real text, fonts/licenses, fixtures, task contract and platform matrix **before** any new builder runs. Use the same coding model, effort, service tier, execution capabilities and feedback policy in both arms. Keep fresh, independent workspaces and randomized execution order. Run sequentially when sharing a local selector or device. No arm sees the other output or the repaired Relay implementation.

| Arm | Available design assistance | Purpose |
| --- | --- | --- |
| Guidance | The same recorded direction and Design Theory's design guidance, ordinary coding and measurement tools; no Design Theory decision engine | Control for the brief and advice |
| Guidance + engine | Identical inputs and guidance, plus the frozen CLI/MCP, local selector and replay tools | Measure the added effect of the toolkit |

An Impeccable-text-only arm can answer a separate comparison with that named workflow. It changes guidance as well as tools, so report it separately. Do not benchmark additional local models. Builders receive the same completion contract and can self-test; no deadline or token cutoff is introduced. Freeze the first declared delivery (including an incomplete or failed one), preserve the entire streamed usage record, and then evaluate without feedback or repairs. Later refinement gets a separate iteration series with identical feedback opportunities. Tool discovery, failures to activate the skill, manual overrides and non-use are outcomes, not reasons to discard an inconvenient run.

Use repeated, independently authored briefs and fresh builds. Reserve unseen content, widths and at least one different art direction for evaluation; do not tune equations against them. Split related surfaces, states and viewports by project so they cannot masquerade as independent projects. A Relay-only result remains a Relay case study.

## Judge complete applications

Give reviewers neutral A/B identifiers, counterbalance left/right and task order, hide condition names and equation scores, and retain accidental unblinding. Both sides must have the same content, task state and scenario. Review actual interactions and transitions as well as matched screenshots. Human responses and synthetic Astra critique remain separate datasets. Self-critique is useful diagnostic material, not an independent preference label.

Record these outcomes separately:

| Outcome | Evidence |
| --- | --- |
| First-pass preference | Human A/B/tie judgments for overall preference, hierarchy/readability, character/coherence and motion/material appropriateness, with a short reason |
| Task usability | Successful diagnosis/resolution and secondary tasks, errors, assistance and time; report learning/order effects |
| Hard failures | Lost content or state, wrong linked counts, contrast/keyboard/focus failures, overflow, clipped hit areas, invalid persistence, reduced-motion or disposal failures; retain actual renderer/platform evidence |
| Responsiveness | Phone 320/390, narrow 768, iPad 834 portrait/landscape and desktop 1440/1920, text enlargement, changed/localized content, day/night and reduced motion; native iOS/Android/iPad measured separately |
| Cost and efficiency | Actual uncached/cached input and output usage, wall time, attempts to acceptance, numeric evaluations, renderer calls, selector calls and cache hits; unknown values remain null |
| Tool influence | Hash-bound authored input → explored candidates → optional local selection → consumed properties → actual measurement → replay; a parameter import alone is insufficient |

Before collecting preference labels, freeze the number of projects/builds/reviewers, exclusions, primary outcome, stopping rule, statistical analysis and practically meaningful adoption threshold. Choose sample size from a stated effect and pilot variability, not after viewing winners. Report uncertainty and ties; repeated screenshots and ratings from one project are correlated, so use project-level paired analysis rather than counting every viewport as an independent win. Hard failures remain visible and cannot be averaged away by preference or low energy. Do not claim improved defaults until preference improves under that predeclared decision rule without unacceptable task or failure regressions. Report cost as a separate trade-off; a preferred design is not automatically cheaper.

## Test mechanisms without declaring beauty

Keep these smaller experiments separate from the main workflow comparison:

* **Musical prior versus smooth prior:** same viable candidates and constraints, held-out projects and blinded preference; discard musical landmarks if they add no predictive value.
* **Selector and replay:** count numeric candidates versus neural decisions, replay unchanged inputs with zero new neural calls, and require changed content/geometry/brief to invalidate the affected path and revalidate facts. This tests saved decision work, not human preference.
* **Bento placement:** compare alternative flex-based arrangements of the same semantic regions; preserve content, reading/focus order and task priority. Check fit, proportions, adjacency and whitespace independently, then use blind judgments and task evidence. Optimality is conditional on the stated search space and priorities, not a universal beauty claim. This capability is requested and not yet implemented in the current Relay integration.
* **Motion/materials:** verify actual intermediate frames, interruption, reduced motion, hidden/disposal behavior, legible composited contrast and platform performance. A spring parameter or material equation is not proof that its adapter visibly uses it.

The improvement loop is: retain a concrete failure, identify the shared factor/adapter/skill defect, repair it, run its regression and the ordered lane, then freeze a new version for the **next** held-out comparison. Preserve the previous result. Improving Relay and proving better defaults are related work with different evidence.
